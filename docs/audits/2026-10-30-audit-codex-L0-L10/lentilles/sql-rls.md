# Lentille sécurité serveur — migrations 0008 à 0013 (commit 247b2e5, lecture seule)

Agent « security-auditor ». Chemins relatifs à ``. Constat I-1 revérifié par moi dans le SQL (voir note en fin).

## 1. Verdict
- L'isolation entre comptes tient : aucun chemin par lequel un compte admis lit, écrit ou purge les lignes d'un autre. Les 15 fonctions `security definer` neuves fixent `search_path=''` et filtrent par `auth.uid()` (ou comparent leur `uid` à `auth.uid()`). `anon` révoqué partout.
- 10 constats : 0 bloquant, 4 importants, 6 mineurs.
- Le plus grave a une échéance : le ménage nocturne des tombales (`purge_tombstones`) lèvera une exception chaque nuit, pour tous les comptes, dès qu'une tombale d'un magasin gardé atteint 90 jours (au plus tôt vers le 11 janvier 2027, à prouver).
- L'effacement d'un compte par `auth.users` est cassé. `l2_lock_rows` est exposé sans borne (déni de service partagé possible, à prouver). Aucune trace d'application de 0011, 0012, 0013 dans `RESULTATS-mitsu.md`.
- Mur = RLS par `owner_id` + filtre `auth.uid()` explicite dans chaque fonction définisseur + révocations `anon`. Dos-d'âne = gardes L1/L2 qui lisent un contexte fourni par le client, et « autorité » `current_user` partagée entre toutes les fonctions du même propriétaire.
- Aucun secret dans `supabase/` ni dans les générateurs ; aucune injection (`execute format` avec `%I` sur liste blanche, valeurs par `using`) ; aucune vue neuve ; aucune table publique neuve ; deux tables privées seulement.

## 2. Constats
### Important
**I-1 · La purge des tombales est cassée par les nouveaux déclencheurs (échéance).** `0005_imports.sql:160-171` : `purge_tombstones` (cron `0001:685`, 04 h 15) fait en une transaction `update public.%I set data='{}' where deleted_at < now()-90 jours` sur 27 magasins, sous `app.maintenance='on'`, sans gestion d'exception, et sous pg_cron `auth.uid()` est nul. Aucune garde neuve ne lit `app.maintenance`. Lèvent alors : `0011:74` (via `l6_guard_version`, toute UPDATE de `recipe_versions`) ; `0012:255` (`cook_sessions`, `timer_launches`) ; `0013:197` (`inventory`) ; `0010:812` (`book_editions`, UPDATE sur `deleted_at` non nul) ; `0010:836` (recette liée à une édition introuvable sous `auth.uid()` nul) ; `0008:76` (recette avec `lifecycle_id`). Scénario : une minuterie supprimée (tombale avec `data`, `src/sync/lots.js:82-84`) → 90 jours plus tard la purge lève, tout est annulé, chaque nuit ; le contenu des tombales est gardé indéfiniment (contraire à la spec § 3.1). Aucun prouveur ne joue `purge_tombstones`. Correctif : sortie anticipée dans les gardes l1/l2/l6/l7/l8 quand `app.maintenance='on'`, `current_user` = propriétaire de `purge_tombstones`, `tg_op='UPDATE'`, `new.data='{}'`, `old.deleted_at is not null` ; prouveur dédié ; surveiller `cron.job_run_details`.
**I-2 · Supprimer un compte par `auth.users` est impossible.** `owner_id … on delete cascade` (`0001:74`) ; la cascade déclenche les gardes sans JWT : `0010:812` (DELETE `book_editions` → `cycle`), `0012:251`, `0013:193` (`auth.uid() is null` → 42501), `0011:85` puis `:74`. « Delete user » échoue dès qu'il existe une édition, version, séance, minuterie ou lot. Si l'adresse est déjà retirée de `private.allowed_users`, `sync_purge_all` est refusée aussi (`0010:948`). Les prouveurs appellent eux-mêmes `sync_purge_all()` avant `delete from auth.users` (`tools/prover-cuisine-concurrence.mjs:26`). Correctif : exception explicite pour la cascade, ou `admin_purge_owner(uid)` réservée à `service_role` ; procédure au README.
**I-3 · `l2_lock_rows` exposé et non borné.** `0009:511` `grant execute … to authenticated` ; `0009:87-94` un `pg_advisory_xact_lock` par id distinct venant de `recipe_contexts`/`edition_contexts`/`items` (client), sans borne ; `sync_push` l'appelle avant de valider le magasin (`0009:211`). 50 000 contextes → 50 000 verrous dans la table partagée → 53200 « out of shared memory » pour les autres sessions (inférence). Correctif : borner (taille et ids distincts, ex. 2 000).
**I-4 · Aucune trace d'application de 0011, 0012, 0013.** `RESULTATS-mitsu.md:573-584` s'arrête à 0010 : ni SHA-256, ni sauvegarde, ni postflight, ni capacités pour trois migrations en production. Le postflight 0010 compare la prod à un catalogue local : un défaut présent des deux côtés n'apparaît pas (M-4). Correctif : postflight lecture seule (`pg_get_functiondef`, droits, triggers) consigné.

### Mineur
**M-1 · Gardes = dos-d'âne.** `0009:341` `set_config('app.l1_write', r::text, true)` où `r` est la ligne du client ; gardes l1/l2 font confiance à `archive_import`, `historique`, `expected_cycle_id` (`0008:77-78`, `0010:840-841`). `0010:896` : `current_user = propriétaire de l5_apply_source_command` est vrai dans toute fonction définisseur du même propriétaire, sous cron et dans l'éditeur SQL ; `l5_transfer` insère des `imports` dont seul `index_storage` est contrôlé (`0010:674,681`) → contourne `l6_guard_journal` (`0011:416`) : un client peut forger un journal « traduction » dans son propre compte. Le commentaire `0010:895` est faux pour L1/L2.
**M-2 · Corps réécrits en prod par expression régulière, absents du dépôt.** `0011:592`, `0012:282`, `0013:222` : `regexp_replace(definition,'begin[[:space:]]',clause,'i'); execute definition`. Le corps réel de `l1_guard_recipe` et `l2_guard_write` n'est dans aucun fichier ; un futur `create or replace` repris de 0010 effacerait les trois exceptions sans bruit. Correctif : réécrire les deux fonctions en entier.
**M-3 · Transferts privés jamais purgés.** `0010:587-592` : pas de clé étrangère vers `auth.users` ; `sync_purge_all` ne les liste pas (`0010:951`) ; `l5_cleanup_transfers` (`0010:756`) réservée à `service_role`, aucun `cron.schedule` ; `header` contient la commande entière du client (`0010:651`).
**M-4 · `sync_push_v2` ouverte à PUBLIC de 0010 à 0011** (`0010:983` sans `revoke from public`, fermé `0011:607`) ; sans effet (42501 si `auth.uid()` nul). Correctif : test `has_function_privilege('anon', …)` sur toutes les fonctions.
**M-5 · Purge client des imports à 30 jours bute sur les gardes serveur (inférence).** `src/model/repo.js:179-190` met en tombale les `imports` fermés > 30 jours ; le serveur refuse (`0011:421`, `0010:918`) → quarantaine « forme » sur l'appareil, ligne gardée au serveur. Pas de fuite.
**M-6 · README obsolète.** `supabase/README.md:3` « cinq migrations générées (0001, 0002, 0003, 0005, 0008) » ; aucune procédure 0009-0013. En revanche 0009-0013 sont couvertes par `--check` (`tools/generer-migrations.test.mjs:273`).

Compatibilité : un vieux client (0.21.1) passe par `sync_push` v1, toujours accordée ; contexte vide → refus « forme » mis en quarantaine sur l'iPhone, aucune corruption serveur. Nouveau client contre fonction absente : `src/sync/transport.js:33` classe PGRST202/42883 en « incompatible ».
